# Autonomous Multi-Agent Habitat (AMH)

A continuously operating habitat for autonomous agents. It wakes from goals, schedules, events, and messages; supplies durable work, context, memory, tools, workers, and recovery; and exposes stable seams on which domain applications are built.

AMH is not a governance product, a security product, a physical-device stack, or a domain application. Small hard core, reversible extensions: the core contains only the invariants every domain requires. Models, harness policies, tools, memory implementations, user surfaces, and domain behavior attach as replaceable, individually installable, individually removable extensions — see `docs/AMH-SPECIFICATION.md` §1 for the full governing decision set. Physical-device actuation in particular is not core at all; it belongs to a separate Physical AI extension, designed and built independently.

## What's real right now

Everything below is working code with tests that exercise it against real processes, a real PostgreSQL instance, and (where applicable) a real network protocol — not mocked.

- **Durable execution.** DBOS Transact on PostgreSQL, the sole authoritative store from day one. A crashed process resumes exactly where it left off, no duplicate committed steps — proven by restart-mid-flight tests on the goal-pursuit workflow.
- **Extension registry (`daemon/extensions`).** Discover, activate, quiesce, dispose against `contracts/extension-manifest.schema.json`; dependency resolution between capability providers and consumers; disposal recorded as activation's verified inverse. Knowledge base, memory, model providers, and harnesses are all just extensions to this registry — it has no domain-specific logic.
- **Computers (`daemon/sandbox`).** Each agent's own isolated compute instance: container-backed via docker, or process-backed via a real Linux mount namespace when no docker daemon is present. Create/Destroy is a verified-inverse pair.
- **Credentials (`daemon/credentials`).** AES-256-GCM encrypted at rest, fails closed with no encryption key configured, rotation-aware, never returns a secret over the admin API.
- **Control-plane UI (`extensions/control-plane-ui`).** Installs harnesses, provisions computers, and authenticates accounts — installed and activated through the extension registry itself, not compiled into the daemon.
- **Authorization.** Two bearer-token roles (agent, operator), constant-time comparison, fail-closed daemon startup if either token is unset. An agent token is mechanically refused on every operator-only route (extension install/activate/dispose, credential writes) — not a convention, enforced by the server.
- **Context management.** Per-tool-result token cap, budget tracking, compaction triggered at a configurable threshold, trace-context propagation across DBOS worker-thread boundaries so a subordinate agent's span nests under its parent's.
- **MCP client.** stdio transport, tested against a real third-party MCP server (pinned, not `npx`-refetched per run). Every MCP tool call the agentic loop (`agents/harness/agentic_loop.py`) makes is now proposed as an external effect through `agents/workflows/operations.py` (§4) first — `amh.core/mcp-client` as `owner_extension_id`, always reversibility `none` since an arbitrary third-party tool has no verified inverse the harness can attest to. That legitimately parks the effect at `needs_approval` permanently (nothing calls `approve`/`deny` on it) — a real, inert audit-trail entry, not a live admission gate: the loop never waits for or acts on the resulting decision, and a failure to even record the effect (daemon unreachable, etc.) is logged and swallowed rather than blocking or failing the tool call it describes. See "What's declared but not yet built" for what this doesn't yet do.
- **Model-provider inference (`daemon/inference`).** Agents call `POST /v1/inference/{complete,count-tokens}` on the daemon using only their agent bearer token; the daemon holds the actual provider credential (registered once as a `daemon/credentials` account) and makes the real call. An `anthropic` kind speaks the native Messages API (API key or OAuth bearer); an `openai_compatible` kind speaks chat completions — between the two, Anthropic, OpenAI, Grok/SuperGrok, GLM/Z.ai's Coding Plan, and self-hosted vLLM/Ollama are all covered without per-vendor code. OAuth subscription tokens refresh and rotate back into the credential store automatically. `agents/context/llm.py` is a pure HTTP client to this seam — it holds no model-provider credential of its own. `agents/context/budget.py`'s token counting is a real tokenizer, not a `chars // 4` approximation. Every `Complete`/`CountTokens`/`Embed` provider attempt is now the first real call site for `daemon/operations` (§4): each is proposed, marked dispatch-pending/dispatched, then resolved confirmed or failed from the real response — a model-provider call declares reversibility `verified` because it has no side effect outside its own response, the same "reversible by construction" category `daemon/sandbox`'s Create/Destroy pair uses. `Router.Operations` is nil-safe (untracked, same soft-disable posture as `Server.Credentials`) for callers that don't wire it; `daemon/api.New` always does.
- **Generic policy and approval seam (`daemon/policy`).** The core's one domain-neutral policy: admit iff a proposed action declares a verified, attested reversibility; everything else needs an operator's Approve/Deny. A `PolicyDecision` is bound to an exact action digest (recomputed server-side from the payload, never trusted from the caller) and single-use — `Consume` atomically fails closed on expiry, a digest mismatch, or reuse. Approving a `needs_approval` decision mints a fresh, freshly-bound decision rather than mutating the original, so every decision's decided-at/expiry stays internally consistent. An agent token is mechanically refused on Approve/Deny — the same anti-self-approval property as every other operator-only route. §15 acceptance invariant #6 ("policy dispatch is bound to the admitted action digest and fails closed after ... mutation") is now real end to end, not just inside `Consume`: `daemon/operations.MarkDispatchPending` used to re-read the digest `Propose` had already stored and hand it straight back to `Consume`'s mismatch check — comparing a value against itself, so the check could never actually fire. It now takes the real dispatch-time payload and hashes it fresh, so an effect admitted for one payload genuinely fails closed (`409`, stays `admitted`) if a different payload is presented at dispatch — proven by tests at the Go-internal seam and, since `POST .../dispatch-pending` now requires a `payload` body, over the real HTTP boundary where a propose-time and dispatch-time payload can actually diverge across two separate requests.
- **A2A 1.0 adapter (`daemon/a2a`).** External A2A clients discover this habitat via an unauthenticated `/.well-known/agent-card.json`, then call `message:send`/`GetTask`/`ListTasks`/`CancelTask` over the HTTP+JSON binding (the one A2A explicitly supports whose method/path mapping is unambiguous straight from the protocol's own proto definitions, unlike the JSON-RPC binding's method-name convention). `SendMessage` durably creates a real AMH Goal — see "What's declared but not yet built" for the one thing it doesn't yet do.
- **Signed extension packs and compatibility qualification (`daemon/extensions`).** `Discover` unconditionally checks a manifest's `spec.compatibility.amhCore` semver range against this daemon build's own `CoreVersion` — an incompatible manifest is refused outright, not merely warned about. If a manifest declares `spec.signature`, `Discover` verifies it for real: the declared digest must equal the manifest's own server-recomputed `SignableDigest` (the same "never trust a caller-supplied digest" property `daemon/policy` enforces for action digests), the `keyId` must resolve to a currently-trusted, non-revoked Ed25519 key in the new `trusted_signing_key` store (`POST/GET /v1/extensions/trusted-keys`, `POST /v1/extensions/trusted-keys/{keyID}/revoke`, all operator-managed), and the signature itself must verify against that key. Real Ed25519 keys, real `ed25519.Verify` calls, real rejection of a tampered manifest, an unknown key, or a revoked key — proven by tests that sign with `crypto/ed25519`, not mocked. `Activate`/`Dispose` — the only two calls here that touch a real OS process or the docker CLI (`launcher.go`) — are now tracked through `daemon/operations` (§4) the same full way `daemon/inference`'s calls are: `owner_extension_id` `amh.core/extensions`, reversibility `verified` (`Dispose` really is `Activate`'s tested inverse), propose → dispatch-pending → dispatched → observed → resolve confirmed/failed. This gets extension activation real crash-recovery reconciliation for the first time — an extension previously stuck `activating` forever after a daemon crash mid-launch now lands its effect at `dispatched` and gets caught by the startup `ReconcileInterrupted` sweep like everything else — and replaces the old `extension_effect` table (write-only, never queried by anything, dropped in migration `0007`) with real, HTTP-queryable effect history. A launch/teardown's own real outcome is always authoritative over whether the *tracking* calls around it succeeded — a successfully-launched extension is never reported failed just because recording that fact afterward hit an error, matching how a genuine mid-launch crash is already meant to be handled. `Registry.Rollback(id, fromVersion, toVersion)` closes §15 acceptance invariant #11 ("rollback restores the prior capability binding") and this package's own doc comment, which already quoted §2.1's "discovery, dependency resolution, activation, quiescence, disposal, and rollback" as its scope before a `Rollback` function actually existed — it composes `Quiesce`+`Dispose`+`Activate` into the one call an operator previously had to script by hand across three (`POST /v1/extensions/rollback`, operator-only like every other extension mutation). It genuinely restores the capability binding — `Dispose` revokes the old version's token, `Activate` mints the restored version a real fresh one, proven over an actual launched process — but honestly, not everything invariant #11 asks for: the three steps aren't atomic (a failed `Activate` after `Dispose` leaves neither version active, inspectable via `Get`, not auto-healed), "compatible persisted state" is out of scope (core has no visibility into an extension's own domain-specific state to verify that half), and the control-plane UI (`extensions/control-plane-ui`) doesn't expose it yet — only `Activate`/`Quiesce`/`Dispose` have buttons today; calling `Rollback` requires the API directly.
- **Cordis disposal order for core-mediated effects (`daemon/extensions`, §15 acceptance invariant #3 / §5.1).** §5.1 requires every core-mediated effect an extension installs (tool registration, event subscription, timer, route, service publication, child-extension mount) to register a disposer at creation and be disposed in reverse registration order — and this package's own doc comment already quoted that requirement as part of its scope with nothing built to back it. Core cannot literally execute an arbitrary extension's disposer itself (only the extension knows how to actually undo a "tool registration" — the same reason §4 says core "SHALL NOT construct an inverse" for external effects), so what's built is what core honestly *can* enforce: an active extension self-reports each core-mediated effect it creates (`POST /v1/extensions/context-effects`, authenticated by its own capability token, the same mechanism invariant #5 already built) and self-reports disposing each one (`POST .../{effectID}/dispose`) — `DisposeContextEffect` fails closed (`409`) unless the target is the most recently registered, still-outstanding effect for that instance, mechanically enforcing reverse order rather than trusting the caller. `Dispose` itself now refuses (`409`, extension left untouched, still `quiescing`) while any registered effect remains undisposed. `kind`/`ref` are free-form and opaque to core — this doesn't hardcode to §5.1's six examples, the same domain-neutral posture every other core primitive already takes. Honestly scoped: this is bookkeeping and order/completeness enforcement only, not a live registration bus — no dynamic tool catalog, event bus, timer service, or route table actually exists in this daemon for an extension to register *into*; an extension using this today is self-attesting that it created and later tore down *something*, and core verifies the self-attested bookkeeping is complete and correctly ordered, not that the underlying effect was real. There's also no client SDK yet — an extension calls the raw HTTP routes itself (no Python `agents/workflows/extensions.py` involvement, since that module is deliberately agent-facing and read-only; extensions are arbitrary external processes, not Python agent code).
- **Real per-run token usage (`daemon/inference`, `agents/context/llm.py`, `agents/workflows/goal.py`, §2.1/§14 cost accounting).** `run.tokens_in`/`run.tokens_out` (`store/migrations/0001_init.sql`) existed since the very first migration but nothing ever wrote to them — both provider paths in `daemon/inference/inference.go` (`anthropicComplete`, `openAICompatibleComplete`) parsed the provider's real response and silently discarded its `usage` block. `Router.Complete` now returns that usage alongside the text, `/v1/inference/complete`'s response carries real `input_tokens`/`output_tokens`, and the `/v1/openai/chat/completions` facade route now populates a real OpenAI-compatible `usage` field too (a genuine compliance improvement for external clients that read it, not just internal bookkeeping). On the Python side, `ModelClient.complete_with_usage()` is a new, additive method (`complete()` itself is untouched — too many existing callers, `decompose_goal` and `llm_summarize` included, depend on its plain-string return) that surfaces the real counts as a `CompletionResult`. `agents/harness/agentic_loop.py`'s per-turn loop now calls it instead of `complete()`, accumulates real totals across every turn into `LoopResult.tokens_in`/`tokens_out`, and `agents/workflows/goal.py`'s `run_subagent` writes them onto the real `run` row via a new `ontology.record_tokens` (additive `UPDATE`, not an overwrite). Proven end to end: a real fake-provider response carrying a `usage` block flows through the real Go daemon and the real Python workflow into a real Postgres `run` row, asserted non-zero. Known gap: tokens are only recorded on the success path — a run that raises before reaching `done` (budget exceeded, an unknown tool, a malformed model response) has no `LoopResult` to read totals from, so whatever partial usage it accrued is not captured. `cost_usd` remains untouched — see "What's declared but not yet built."
- **Contract validation for model/tool output (`agents/harness/contract_validator.py`, §11).** §11's self-healing table names "contract validator" as the recovery owner for "invalid model/tool output," but nothing backed that until now — `agents/harness/agentic_loop.py` only ever did ad hoc `isinstance`/key checks on the model's parsed JSON, and tool-call `args` were never validated against anything: an MCP tool's own server-declared `input_schema` was already being fetched via `list_tools()` and then completely ignored. Two real checks now exist. `validate_action` checks the model's whole turn against a new `contracts/agent-action.schema.json` — same pass/fail outcome as the old ad hoc check for every case already tested (a malformed envelope still raises and kills the run, a deliberate choice left unchanged this round — see below), just backed by real schema validation instead of hand-rolled checks. `validate_tool_args` checks a tool call's `args` before dispatch — `BUILTIN_ARG_SCHEMAS` for the seven built-in tools, or an MCP tool's own real `input_schema` for MCP calls — and a failure is fed back as a recoverable `"error: ..."` turn, the same posture every other tool-execution error already gets, not a crash. This closes a real, demonstrated gap: `write_file` called with a non-string `path` used to raise a bare, uncaught `TypeError` from inside `pathlib`'s `/` operator (not one of `_dispatch_builtin_tool`'s caught exception types) and kill the whole subagent run; an MCP call with invalid args used to be proposed as a tracked effect and sent straight to the third-party server with zero local checking. Both are now caught before anything happens — proven by tests against the real filesystem MCP server fixture, not a mock, confirming the file is never created and the effect is never proposed. Deliberately unchanged: whether a malformed top-level response (bad JSON, missing `tool` key, an unknown tool name) should also become a recoverable retry turn instead of a hard raise — that's a bigger design change this round explicitly did not make (see `run_agentic_loop`'s own docstring for why "never returns fabricated success" is a deliberate contract, and `test_malformed_json_response_raises`/`test_unknown_tool_name_raises` for the behavior it still has).
- **Retry classification is a real, enforced pre-dispatch requirement (`daemon/operations`, §4).** §4 lists "retry classification" among what "the owning extension SHALL supply" before dispatch, and `contracts/action-envelope.schema.json` already declared `retryClass` required with a fixed three-value enum (`never`/`reconcile_before_retry`/`idempotent`) — but nothing enforced it: `daemon/operations.ProposeRequest` had no such field, `effect_record` didn't persist it, and none of the three real Propose call sites supplied one. `Propose` now fails closed (a real error, both at the Go-internal seam and over `POST /v1/operations`) if `retry_class` is missing or not one of the three values — the same "declared, not inferred" posture every other pre-dispatch requirement here already has. Persisted on `effect_record` (new migration `0010`) and returned on every effect response, matching how `forward_digest` is already stored for inspection. All three real call sites now supply a real, honest classification: `daemon/inference` (a model completion has no idempotency key and isn't guaranteed to reproduce the same response), `daemon/extensions` (launching or tearing down a real process isn't safely repeatable), and `agents/workflows/operations.py`'s MCP tool-call tracking (an arbitrary third-party tool call has no known retry story, matching its already-honest `reversibility="none"` default) — all three are `never`. Explicitly not touched: idempotency mechanism (§4 says "if available" — genuinely optional, and no real call site has one to declare) and observation/reconciliation method plus timeout/uncertainty behavior, neither of which has a concrete schema-backed shape anywhere in this codebase to build against yet.
- **Dependency-cycle safety proven, not just assumed (`daemon/extensions`, §5.2).** §5.2 asks that two extensions requiring each other's capability be refused, not left to hang — the ledger initially flagged this "not started," since no dedicated cycle-detection code exists anywhere in `daemon/extensions`. Direct inspection shows none is needed: `Activate`'s `requirementSatisfied` check is a single non-recursive query against currently-`active` extensions, with no transitive or recursive resolution anywhere in the package for a cycle to loop through — the same "holds by construction" posture already documented for §15 invariant #10. A new real, timeout-bounded test (`TestActivate_MutualRequirementCycle_FailsFastNeitherHangsNorActivates`) proves it rather than merely asserting it from code review: two manifests with a genuine mutual capability requirement, both `Activate` calls attempted, both fail fast with `ErrMissingRequirement` well under a 5-second bound, neither extension's status mutated. This is a regression guard as much as a proof — a future change that *does* introduce recursive dependency resolution would have to actually break this test, not just violate an assumption nobody was checking.
- **Quiesce/dispose ordering proven end to end (`daemon/extensions`, §5.2 / §15 invariant #4).** §5.2 requires dependency removal to quiesce/dispose consumers before their providers. Only `Quiesce`'s own refusal (`TestQuiesce_RefusesWhileActiveDependentExists`) was previously tested directly; the full ordering guarantee itself wasn't. Direct inspection confirms it holds by construction: `Dispose` requires status `quiescing`, a state only `Quiesce` can set and only once it succeeds, and `Quiesce` refuses outright (`ErrActiveDependents`) while any active extension still non-optionally requires a capability this one provides — so a provider can never reach `Dispose` while an active consumer needs it, not via separate ordering logic inside `Dispose`, but because `Quiesce` is the sole gate into the state `Dispose` requires. `TestQuiesceDisposeOrdering_ProviderNeverDisposedBeforeItsConsumer` proves this end to end: both `Quiesce` and `Dispose` refused on the provider while its consumer is active, neither mutating its status, then both succeeding in sequence once the consumer is itself quiesced and disposed.
- **Backup and restore (`daemon/backup`).** `POST /v1/backup` streams a real `pg_dump` custom-format snapshot of the daemon's own PostgreSQL store; `POST /v1/restore` applies one back via `pg_restore --clean --if-exists --single-transaction` — atomic: either the whole restore commits or the target is left exactly as it was. Both are operator-only. Proven by a real round-trip test: seed a row, back up, mutate further, restore, and confirm the post-backup mutation is gone while the pre-backup row is back.
- **Migration rollback (`daemon/store`).** Every migration under `store/migrations/*.sql` now has a paired reverse migration under `store/migrations/down/` (same filename). `store.Rollback` finds the most recently applied migration from `schema_migrations`, requires its down-file to exist — failing closed with `ErrNoDownMigration` rather than silently no-op'ing or reversing the wrong one — and applies it in a transaction. `amh-daemon -rollback-migration=N` runs it N times and exits, without starting the daemon; it's a maintenance operation against a stopped daemon, not a live admin-API route, since rolling back a schema out from under an actively-serving process is a different, riskier thing than backup/restore is. Proven by tests that roll every currently-defined migration all the way back to an empty schema, then re-apply forward cleanly.
- **External-effect lifecycle (`daemon/operations`).** §4's generic operation state machine — `PROPOSED -> ADMITTED|REJECTED|NEEDS_APPROVAL -> DISPATCH_PENDING -> DISPATCHED -> OBSERVED|OUTCOME_UNKNOWN -> CONFIRMED|RECONCILED|COMPENSATED|FAILED` — as real, durable, tested mechanics, not just a diagram in the spec. `Propose` composes with `daemon/policy` for admission rather than reimplementing it; `MarkDispatchPending` consumes the admitting `PolicyDecision` atomically, the caller's durable commitment to actually attempt the external call next. `ReconcileInterrupted` runs once at daemon startup, before anything else touches operations: it finds every effect still `dispatched` — meaning nothing ever recorded what happened to it, because whatever was tracking it was interrupted first — and marks each `outcome_unknown`. This is what makes acceptance invariant #2 ("interrupted external effects enter reconciliation and can remain `OUTCOME_UNKNOWN`") a property this daemon actually has, not merely documents: proven by a test that creates an effect stuck `dispatched` (simulating a crash mid-dispatch), calls `ReconcileInterrupted`, and confirms it — and only it — becomes `outcome_unknown`, plus a real CLI-level smoke test (build the binary, seed a stuck effect via SQL, restart, confirm the daemon's own startup log and the database agree). `Resolve`'s terminal-outcome argument is trusted from the caller by design, not oversight — see `daemon/operations`'s doc comment for why that's the opposite posture from `daemon/selfimprove`'s server-computed verdict, and is what §4 itself requires ("AMH SHALL NOT infer that the effect failed... or select a domain recovery action").
- **Extension effect-ownership authorization (`daemon/extensions`, `daemon/api`).** §15 acceptance invariant #5 — "an extension cannot mutate another extension's owned effects" — was, until this landed, entirely unenforced: `daemon/operations`' HTTP routes never checked a caller against an effect's `owner_extension_id`, and `daemon/authn` has only two static, global roles, no per-extension identity at all. `Activate` now mints a fresh, random capability token per activated instance (`daemon/extensions/capability.go`; skipped for `in_process` isolation, which has no separate process to authenticate), stores only its SHA-256 hash, and injects the raw token as `AMH_EXTENSION_TOKEN` into the launched process's (or container's) own environment — never returned by any API response. `Dispose` revokes it unconditionally, even if teardown itself failed. `daemon/api`'s mutating operations routes (`Propose` and every state-transition route past it) now call `authorizeEffectOwner`: an operator always passes; a core-owned `owner_extension_id` (the `amh.core/` prefix every real core call site already self-labels with) needs nothing beyond the ordinary agent/operator check every route already had; anything else requires the request to carry that exact extension's own capability token in a new `X-AMH-Extension-Token` header. Proven end to end by tests that Activate a real `IsolationProcess` extension over HTTP, read its real token back from a file the launched process itself writes (the only legitimate way to observe one — nothing here exposes a token any other way), and confirm it's required, extension-specific, and bypassable only by an operator. Building this test surfaced and fixed a real, pre-existing concurrency bug in `daemon/extensions/launcher.go`: `teardown()` was calling `cmd.Wait()` a second time on the same `*exec.Cmd` while `launch()`'s own background goroutine already had an in-flight `Wait()` call on it — Go's `os/exec` explicitly forbids concurrent/repeated `Wait()` calls (undefined behavior, observed as `teardown()` hanging forever). Now exactly one goroutine ever calls `Wait()` for a process's whole lifetime, with `teardown()` consuming its result over a channel instead.
- **Goal dispatcher (`agents/workflows/dispatcher.py`).** §3.1's "deterministic delivery of external triggers into DBOS using stable idempotency keys" — the first standing, long-running Python process this codebase has ever had. `claim_and_dispatch_once` starts `pursue_goal` for every still-`open` goal under a workflow ID derived from the goal's own id (`f"goal-{goal_id}"`); DBOS's own workflow-id deduplication, not a mutating claim step, is what makes repeated or concurrent dispatch attempts for the same goal safe — `DBOS.start_workflow` under a workflow ID it has already seen returns a handle to the existing run instead of starting a second one. That's deliberate: a mutating "claim" (flip status, then start the workflow) would leave a crash window where a goal could end up claimed but never actually dispatched; relying purely on DBOS's dedup has no such window, at the cost of a harmless, idempotent re-dispatch attempt on every poll tick for a goal still in flight. `run_forever` is the standing process (`init_dbos` + `DBOS.launch()` once, then poll). `cancel_interrupted_goals_once` is the other half: every currently-`canceled` goal (`daemon/a2a`'s `CancelTask` sets this synchronously) gets a real `DBOS.cancel_workflow(f"goal-{goal_id}", cancel_children=True)` call every poll tick — an idempotent SQL update under the hood, so repeating it for a goal that's already stopped or already finished is harmless, the same tolerant-polling posture `claim_and_dispatch_once` already has. This is what actually interrupts an in-flight `pursue_goal` run (and its already-started `run_subagent` children) instead of leaving `CancelTask`'s status flip cosmetic — proven by a real test: a goal whose subagent is genuinely blocked in a slow model call gets cancelled mid-flight, and `pursue_goal`'s own workflow handle raises `DBOSAwaitedWorkflowCancelledError` in well under a second, not after the slow call would have otherwise finished. Proven by tests against a real running daemon and a real DBOS instance: a goal inserted with `status='open'` (exactly what `daemon/a2a`'s `SendMessage` inserts) runs to completion, non-open goals are ignored, and calling the dispatcher twice for the same still-open goal doesn't double-run `decompose_goal` (asserted via task count, not just a returned handle).
- **Cognition-worker supervision (`daemon/cognition`).** docs/AMH-SPECIFICATION.md §11's self-healing ownership table names it explicitly: "Python cognition worker | Go supervisor; DBOS resumes durable workflow." `cognition.Worker.Run` shells out to an operator-configured `AMH_COGNITION_WORKER_CMD` (e.g. the goal dispatcher above) via `exec.CommandContext`, registered as one more `supervisor.Child` alongside `api`/`mcp`/`a2a` — a crashing cognition worker now gets the same automatic `OneForOne` restart every other child does, real Go-owned supervision this codebase never had before. Any exit while the daemon is still running — clean or not — is reported as an error (a "run forever" worker exiting at all is unexpected, so only a shutdown-driven exit is treated as clean), which is what actually trips the restart. `cmd.Cancel` sends `SIGTERM` with a 5-second `WaitDelay` before a hard kill on daemon shutdown, the same grace period `api.Server.Run`'s own HTTP shutdown already uses, giving the worker a chance to run its own cleanup. Command parsing is the same non-shell `strings.Fields` convention `daemon/extensions/launcher.go`'s `IsolationProcess` already uses — deliberately not hardcoded to Python or any particular path, so the Go core stays agnostic to how the cognition layer is actually invoked. Unset (the default) is a soft-disable proven by its own test: the daemon starts and runs exactly as before this package existed. Proven end to end by a real CLI smoke test: the built `amh-daemon` binary launching a real shell script as a genuine child process, confirmed alive via `ps`, then confirmed to receive `SIGTERM` and exit cleanly on daemon shutdown.
- **Self-improvement candidate lifecycle (`daemon/selfimprove`).** `GENERATED -> EVALUATED -> CANARY -> PROMOTED | REJECTED; PROMOTED -> DEMOTED -> ROLLED_BACK`, for five candidate classes (prompt, retrieval policy, skill, module, core code). `Generate` is agent-or-operator; every other route — `RecordEval` included — is operator-only: the daemon always computes the pass/fail verdict itself from raw per-case results against a fixed threshold, but a server-computed verdict over caller-supplied measurements isn't independent if the same agent token that proposed the candidate can also submit its own passing results, so recording evidence sits at the operator tier, not the "agents propose" tier. `Promote` requires a passing eval recorded at-or-after entering canary (not merely a historical pass), demotes whatever else of the same class was previously promoted, and records that as the new candidate's rollback target so `Rollback` can restore the prior binding — failing closed if a third candidate has since been promoted over both, and serialized per class with a Postgres advisory lock (plus a partial unique index as a database-level backstop) so two candidates of the same class can never end up simultaneously promoted.

## What's declared but not yet built

Stated plainly rather than hidden in a roadmap: this repository has never obtained a live OAuth session against a real subscription provider (Codex, Grok) end to end, because the network egress this code has been developed under blocks the vendor auth domains — the OAuth refresh mechanism itself is real and tested, but has only been exercised against a fake token endpoint, not a real one. OpenAI Codex under a ChatGPT subscription is deliberately unimplemented — see `daemon/inference/inference.go`'s doc comment for why.

**A goal now dispatches itself, and the daemon can now supervise the mechanism that does — but neither is on by default.** `agents/workflows/dispatcher.py`'s `run_forever` is a real standing process, and `daemon/cognition` can now genuinely supervise it as a restart-on-crash child of `amh-daemon` (§11's "Python cognition worker | Go supervisor," satisfied for real). But `AMH_COGNITION_WORKER_CMD` is unset by default, and there is still no default invocation baked into any `docker-compose`/deployment script this repository ships (there isn't one) — a habitat that doesn't either set that variable or separately run `python -m workflows.dispatcher` under its own process manager still sees a goal created through the A2A adapter sit in `TASK_STATE_SUBMITTED` forever, exactly as before either module existed. The gap has moved twice now: from "the mechanism doesn't exist," to "the mechanism exists but nothing starts it," to "the mechanism to start *and* supervise it exists but isn't configured by default" — each real progress, none of them "solved," worth stating plainly each time rather than letting the caveat go stale. Also unaddressed: the dispatcher polls on a fixed interval (`AMH_DISPATCHER_POLL_INTERVAL_SEC`, default 2s) rather than reacting to a goal's creation immediately — a goal can sit up to one interval before its first dispatch attempt, not truly "deterministic delivery" in the zero-latency sense, just bounded-latency, idempotent, eventually-certain delivery. `AMH_COGNITION_WORKER_CMD` is also a single command line, not shell syntax — no quoting, pipes, or redirection, the same non-shell parsing limitation `daemon/extensions/launcher.go`'s `IsolationProcess` already has, and only one worker process is supervised at a time (no replica count).

**A2A's other scope cuts.** `daemon/a2a` implements Agent Card discovery, `message:send` (new tasks only — continuing an existing task's conversation is unimplemented), `GetTask`, `ListTasks`, `CancelTask`. Not implemented: `SendStreamingMessage`/`SubscribeToTask` (SSE streaming), push-notification config CRUD, `GetExtendedAgentCard`, multi-tenant `tenant` routing, and per-external-caller authentication (the Agent Card declares a Bearer scheme but the adapter reuses AMH's own internal agent/operator tokens — there is no separate identity system for external A2A callers yet). `CancelTask` itself is still Go-side bookkeeping only (there's no synchronous call path from Go into Python's DBOS), but an in-flight `pursue_goal` run genuinely is interrupted now, asynchronously — see the goal dispatcher bullet above for `cancel_interrupted_goals_once`.

**Signing is verified but not mandatory by default.** `AMH_EXTENSIONS_REQUIRE_SIGNATURES` (`daemon/extensions.Registry.RequireSignatures`) defaults to `false` — an unsigned manifest is admitted exactly as it always was. This is a deliberate, documented scope cut, not a silent gap: every manifest shipped in this repository today (`extensions/control-plane-ui/extension.json`, the test fixtures) is unsigned, and flipping the default on would strand them without also minting and distributing real keys for them, which is a packaging/release-process decision this repository doesn't make on its own. A manifest that *does* declare a signature is always verified regardless of this setting — nothing here accepts a forged or tampered signed manifest either way. Key rotation is register-new-keyId-then-revoke-old, with no automated notification to anything that discovered an extension under a since-revoked key — revocation is forward-looking only, the same posture `daemon/credentials.RevokeAccount` already takes.

**MCP tool calls are tracked, not enforced or reconciled — everything else real is now full-lifecycle.** `daemon/inference` and `daemon/extensions`' `Activate`/`Dispose` both get the complete `daemon/operations` treatment (dispatch tracking, crash-recovery reconciliation via `ReconcileInterrupted`, and — since both declare reversibility `verified` — real policy admission), but `agents/harness/agentic_loop.py`'s MCP call site still only proposes: since a bare third-party MCP tool has no verified inverse the harness can attest to, its effect always resolves to `needs_approval` and stays there — nothing ever calls `mark_dispatch_pending`/`mark_dispatched`/`mark_observed`/`resolve` on it (those transitions require `admitted` first), so there is no dispatch tracking, no crash-recovery reconciliation, and no policy enforcement (the loop runs the tool call regardless of the resulting decision) for MCP calls the way the other two call sites get. Turning MCP's proposal-only tracking into the same full lifecycle would require either a real reversibility story for arbitrary third-party tools (out of this repository's control) or a policy path that admits declared-but-unverified effects for calls an operator has pre-approved by class — both genuinely separate, undecided follow-on work. Two more narrower, accepted gaps, both inherited from `daemon/operations` itself: this package tracks exactly one attempt per `operation_id` (`contracts/effect-record.schema.json`'s `sequence`/`attempt` fields for multi-attempt retry orchestration aren't populated — each provider in an inference failover chain gets its own fresh `operation_id` rather than sharing one across attempts), and `MarkDispatchPending`'s policy-decision-consume and its own state update are two separate transactions — a crash in the narrow window between them leaves an effect visibly stuck `admitted` with an already-consumed decision, inspectable by an operator, not silently corrupted, but not fully atomic either.

**Two of five, deliberately, not five of five.** §14 groups "backup/restore, upgrade/rollback, corruption recovery, resource exhaustion, and soak acceptance" as one line item; only the first two are built. Corruption recovery, resource-exhaustion handling, and soak acceptance testing remain undone, not silently assumed covered by having backup/restore and migration rollback. `daemon/backup` also requires `pg_dump`/`pg_restore` to be present on the daemon's `PATH` — the same PostgreSQL client tools any Postgres deployment already installs alongside the server, not an extra dependency this repository introduces, but a real deployment prerequisite worth stating rather than leaving implicit. Migration rollback's down-migration for 0003 (`ALTER TABLE goal ... DROP COLUMN status_message` / narrowing `goal_status_check` back to its pre-A2A set) will fail, as it should, if any row's status is currently `'canceled'` — that's real data with no safe automatic replacement value, not a bug.

**Compaction preserves all 8 required checkpoint fields — but the default strategy can only genuinely populate 3 of them.** Per §7 rule 6 / acceptance invariant #8, `agents/context/compactor.py`'s `Checkpoint` dataclass now carries all 8 required fields (goal, governing constraints, completion predicate, unresolved decisions, failures, uncertainty, active plan, artifact references), and `agents/harness/agentic_loop.py` threads the real objective through so `Compactor.compact()` can populate `goal`. But `extractive_summarize` — the default strategy, chosen because it needs no configuration — is genuinely offline and non-semantic: it can only mechanically recover `goal` (from the passed-in objective), `failures` (from turns already prefixed `"error: "`), and `artifact_references` (a real path/URI scan). `governing_constraints`, `completion_predicate`, `unresolved_decisions`, and `uncertainty` stay honestly `None`/empty under the default, not fabricated. `llm_summarize(client)` is real and tested — it requests and parses all 8 fields as structured JSON from a real model call, the same fail-honest posture as `decompose_goal` — but no call site in this repository passes `summarize=llm_summarize(client)` to `Compactor` today; `agentic_loop.py`'s `compactor or Compactor()` always gets the offline default. A habitat wanting a fully-populated checkpoint on every compaction has to wire that in itself.

**Self-improvement has no candidates to improve yet.** `daemon/selfimprove` is real, generic, tested lifecycle machinery — but nothing in this codebase is a candidate-GENERATING optimizer (GEPA, ACE, Voyager-style skill extraction, DSPy optimizers are named in §10 as "replaceable modules," none implemented here), so nothing calls `Generate` with a real produced candidate today. And no existing prompt/skill/retrieval-policy call site (the hardcoded prompts in `agents/workflows/goal.py`, for instance) reads from or rebinds to a `Promote`d `CandidateVersion` — promotion is real, durable state, not yet a live capability switch. "Canary" is a stricter evidence bar, not actual live traffic-splitting; no request-routing infrastructure to divert a fraction of real calls to a canary candidate exists.

**Tokens are real, cost is not.** `run.tokens_in`/`run.tokens_out` now reflect genuine provider-reported usage (see the cost-accounting bullet above), but `run.cost_usd` stays at its schema default of `0` — no $/token pricing table exists anywhere in this codebase for any provider or model, so computing a real dollar figure would mean inventing pricing data rather than reading it from somewhere authoritative. §2.1/§14's "cost accounting" is half real: the "tokens" half, not the "cost" half.

## Contributing

`docs/AMH-SPECIFICATION.md` is normative — it states what the core is required to provide, what belongs to an extension, and what is explicitly excluded. Read §1 (governing decisions) and §2 (system boundary) before adding anything to `daemon/` or `agents/workflows/`; if what you're adding is domain-specific, it almost certainly belongs in an extension under `extensions/`, not in core.

`contracts/` schemas are the stable, versioned interface between core and extensions. A domain extension publishes its own namespaced schemas; it does not modify a core schema to add a domain entity.
